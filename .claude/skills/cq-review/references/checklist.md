# コード品質チェックリスト (Readable Code / Clean Code 観点)

cq-metrics.py のフラグ箇所を意味的に判断するときの観点。

## 1. 関数化・重複 (DRY)
- [ ] コピペ由来の重複がないか (cq-metrics の Duplicated blocks を起点に)
- [ ] 重複の共通化が**妥当か**も判断する: 偶然似ているだけのコードを無理に共通化すると
      逆に結合が生まれる。「同じ理由で同時に変わるか」で判断
- [ ] 関数は 1 つのことをしているか (「AとBをやってからCする」関数は分割候補)
- [ ] 抽象化レベルが揃っているか (高レベルの流れと低レベルのビット操作が同居していないか)

## 2. 結合度・凝集度
- [ ] 関数が呼び出し元の内部状態を知りすぎていないか (引数で渡すべきものをグローバル/メンバ経由で見ていないか)
- [ ] 出力引数より戻り値を使えないか
- [ ] フラグ引数 (bool で挙動が分岐) は分割候補
- [ ] モジュール境界を越えたデータ構造の直接操作がないか (getter 連鎖 a.b().c().d())
- [ ] 変更が 1 箇所で済むか: この機能を変えるとき何ファイル触るかを想像する

## 3. 制御フロー
- [ ] ネストは早期 return / ガード節で浅くできないか (cq-metrics の Deep nesting を起点に)
- [ ] ループ内の条件分岐はループ分割や関数化で単純にできないか
- [ ] 条件式は肯定形・説明変数で読み下せるか (`if (!(!a || b))` を許さない)
- [ ] switch/if 連鎖が複数箇所に同じ形で現れていないか (テーブル化・ポリモーフィズム候補)

## 4. 命名
- [ ] 名前から挙動が予想でき、予想と実際が一致するか (get が重い処理をしていないか)
- [ ] スコープの広さと名前の長さが釣り合っているか (広いスコープほど説明的に)
- [ ] 単位・条件を名前に含めるべきでないか (timeout → timeout_ms, size → size_bytes)

## 5. エラー処理
- [ ] エラーの握りつぶし (無視される戻り値、空 catch) がないか
- [ ] エラーパスでのリソース解放・状態復元が揃っているか
- [ ] 「起きないはず」の分岐に assert/unreachable を置いているか

## 6. コメント
- [ ] コードから分かることをコメントで繰り返していないか
- [ ] コードから分からないこと (なぜこの方式か、制約、単位) がコメントされているか

## 7. テスト容易性
- [ ] この関数を単体でテストできるか (できないなら結合度の問題のサイン)
- [ ] 境界条件 (0、空、最大、負) のテストが書ける仕様になっているか

## 8. 計算量・メモリ
- [ ] ループ内に入力サイズに比例する操作が入っていないか
      (線形検索、文字列連結 +=、配列先頭への挿入、ループ内 remove — accidental O(N^2) の典型)
- [ ] 時間または追加メモリが O(N^2) 以上なら、想定入力規模と許容根拠が明示されているか
      (根拠なしの N^2 は深刻度: 高で指摘。N に固定上限があり根拠が書いてあれば問題なし)
- [ ] 全データの一括読み込みが必要か (ストリーム/逐次処理で済まないか)
