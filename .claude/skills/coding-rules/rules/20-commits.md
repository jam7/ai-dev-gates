# 20: コミットの分け方

書いたコードをどう区切って記録するかのルール。**分割の判断は書く前にしかできない**
ので、実装を始める時点で「これは何個の変更か」を決めておく。

### COMMIT-1: 1 コミット = 1 つの論理変更 [MUST] [構造]
- 対象: 全言語・全変更
- 規則: 独立した変更を 1 コミットに混ぜない。関連していても、片方だけ取り消せる
  必要があるなら別コミットにする。規模は基準にしない — 20 ファイルの一括改名は
  1 変更、3 行で 2 箇所のバグを直したら 2 変更
- 理由: **混ぜたコミットは、後から一部だけ取り消せない**。revert すれば巻き添えが
  出るし、履歴から消すには filter-repo でパスを狙い撃ちしてメッセージまで
  書き直すことになり、他のコミットのハッシュも変わる。分けてあれば
  `git revert` か `reset` の 1 コマンドで済む
- 悪い例: 「Python 対応を追加し、ついでにゲートを導入し、install.sh の事故も直した」
  / 良い例: 3 コミットに分ける

### COMMIT-2: 混ざりやすい組み合わせを覚えておく [SHOULD] [構造]
- 対象: 全言語・全変更
- 規則: 次の形になったら、意識して分割を検討する
  - 機能追加 + **それを使うための設定**
  - バグ修正 + **周辺のリファクタリング**
  - ツール導入 + **そのツールが出した指摘への対応**
  - 実装 + **それに合わせたドキュメント更新** (同時が自然なこともあるが、
    ドキュメントだけ後から直したくなる場合は分ける)
- 理由: どれも「ついでにやった方が早い」と感じる組み合わせで、しかも後から
  片方だけ要らなくなる可能性が高い
- 良い例: ツールを入れるコミットと、そのツールの指摘を返済するコミットを分ける

### COMMIT-3: メッセージが 2 つのことを言っていたら分ける [SHOULD] [細部]
- 対象: 全言語・全変更
- 規則: コミットメッセージの件名を書いてみて「A し、ついでに B した」の形に
  なったら、分割の合図とみなす。件名に `, and` / 「〜し、また〜」が出るのは典型
- 理由: **書いた本人が自白している**。件名を 1 つの動詞句で書けないなら、
  変更は 1 つでない可能性が高い (名詞の並列は該当しない。
  「Update README for A and B」は 1 変更)
- 悪い例: `cq-metrics: measure Python, and put this repository behind the gate`
  / 良い例: `cq-metrics: measure Python as well as the brace languages`
