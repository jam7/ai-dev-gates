# 90: ルールファイルの書き方 (このファイルはお手本。実ルールではない)

新しいルールは `rules/NN-<topic>.md` として追加し、git commit で共有する。
NN は読み込み順で、番号の大きいファイルが優先 (後勝ち)。
不要になったデフォルトルールは対応する `.md` を削除すれば無効化できる
(`.template.md` は原本として残る。復活させたいときはそこからコピー)。

## 番号の振り方

番号は読み込み順であり、そのまま**優先度の宣言**でもある (矛盾したら番号の大きい
方が勝つ)。どちらの帯に置くかは 2 つの軸で決める。

1. **具体が一般に勝つ** — 原則より各論を強くする
2. **取り返せないものが勝つ** — 後から直せる話より、直せない話を強くする

| 帯 | 役割 | 現在のファイル |
|---|---|---|
| 00-09 | 全体に効く原則 | 00-principles |
| 10-19 | 性能 (計算量・メモリの申告) | 10-complexity |
| 20-29 | 履歴 (コミットの分け方) | 20-commits |
| 30-39 | テスト | 30-tests |
| 40-49 | ドキュメントからの参照 | 40-references |
| 50-59 | 観測 (ログ・エラーの伝え方) | 50-logging |
| 60-69 | 実行時の正しさ (並行) | 60-concurrency |
| 70-79 | 取り返しのつかないもの (実データ・秘密) | 70-real-data |
| 80-89 | そのリポジトリ固有のルール | 空 |
| 90-99 | メタ (書式・運用。実ルールではない) | 90-rule-format |

並びが効くのは、実際に競合する帯どうしだけ。競合したときに勝つ帯の例:

- 性能のためにログを削る → 50 が勝つ (削らない)
- 並行安全のために構造体を増やす → 60 が勝つ (増やしてよい)
- テストの検出力を上げるため実物を貼る → 70 が勝つ (貼らない)

- 追加は帯内の次の空き番号を使う (並行の 2 本目なら `61-timeouts.md`)
- **番号は再利用しない**。退役しても空き番号のまま残す
- 帯が埋まったら新しいファイルを作らず、その帯の既存ファイルに節を足す
- **80 帯は各リポジトリの持ち物**。install.sh が rules/ を丸ごとコピーするので、
  配布元に置いたものは配布先へ一緒に出ていく。配布元では空にしておく

## 書式

1 ルール 1 ブロックで書く:

```markdown
### <ID>: <一言サマリー> [MUST|SHOULD] [構造|細部]
- 対象: (言語やパス。例: C++ のみ / tests/ 以下は除外)
- 規則: (何をする / しない)
- 理由: (なぜ。レビューで「なぜダメ?」と聞かれたときの答え)
- 悪い例 / 良い例: (短く)
```

- **MUST** = 常に守る / **SHOULD** = 原則守る。外れるときは準拠メモに理由を書く
- **構造** = 既存コードと矛盾してもルール優先 / **細部** = 周囲の既存コード優先

## 記入例

### NAME-1: 単位を名前に含める [SHOULD] [細部]
- 対象: 全言語
- 規則: 時間・サイズを表す変数名は単位を接尾辞にする
- 理由: 呼び出し側の単位取り違え (秒とミリ秒など) を防ぐ
- 悪い例: `int timeout;` / 良い例: `int timeout_ms;`

### ERR-1: エラーを握りつぶさない [MUST] [構造]
- 対象: 全言語
- 規則: 戻り値のエラーコードを無視しない。処理できないエラーは呼び出し元へ伝播する
- 理由: 握りつぶしたエラーは離れた場所で別の症状として現れ、調査コストが跳ね上がる
- 悪い例: `(void)write(...);` / 良い例: エラーを返すか、無視してよい根拠をコメントで書く
