# 60: 並行実行の安全性

非同期の呼び出しが**重なって走る**前提で書く。重ならない前提で書いたコードは、
テストでは通り、実データの量で初めて壊れる。そのとき症状は「まれに違う結果が
返る」「まれに空になる」で、再現手順が書けない形をしている。

### CONC-1: 非同期メソッド間の状態をインスタンス変数で持たない [MUST] [構造]
- 対象: 全言語。async/await・コルーチン・Promise・future を持つコード
- 規則: あるメソッドが中断点 (await 相当) を挟んで読み書きする途中経過を、
  インスタンス変数 (メンバ・フィールド) に置かない。**結果は戻り値で返す**。
  複数の値を返したいなら構造体・レコード・タプルにする
- 理由: 中断のたびに制御が手放されるので、同じメソッドの 2 本目が同じ変数を
  上書きする。1 本目が再開したとき読むのは 2 本目の値で、**どちらの呼び出しも
  間違った答えを返す**。呼び出しが 1 本のうちは完全に正しく動くため、
  レビューでもテストでも見つからない
- 悪い例: `_cur = await fetch(x); return build(_cur);` (メンバに置く)
  / 良い例: `cur = await fetch(x); return build(cur);` (局所変数で持つ)

### CONC-2: 共有資源への出入りは排他する [MUST] [構造]
- 対象: 全言語。ファイル・DB・索引・一時ファイルなど、複数の呼び出しが触るもの
- 規則: 同じ資源へ書く経路が 2 本以上あるなら、**書いている間は 1 本だけ**に
  する。走っている間に来た要求は、捨てるのではなく「あとでもう一度」と印を
  付けて、終わったときに拾う
- 理由: 一時ファイルを作って本体に置き換える形の書き込みは、2 本が重なると
  同じ一時ファイルを奪い合う。捨てると**最後の変更が消える**
- 悪い例: `if (busy) return;` だけで戻る (その変更は永久に書かれない)
  / 良い例: `if (busy) { needs_rerun = true; return; }` と、終了時の拾い直し

### CONC-3: 一括処理は「並行で呼ばれる」前提で設計する [SHOULD] [構造]
- 対象: 全言語。まとめて走らせる処理 (一覧の先読み、派生データの生成、同期)
- 規則: そういう処理を書くときは、**同時に何本走るか**を最初に決めて書く。
  1 本ずつしか走らない前提を置くなら、それを名前かコメントに書く
- 理由: 「今は 1 本ずつ」は仕様ではなく、たまたま呼び出し側がそうしているだけの
  ことが多い。後から並列化した人が、その前提が書かれていないので気づけない
- 悪い例: 走査結果をメンバへ溜める一括処理 / 良い例: 1 件ごとに完結させ、
  結果を呼び出し側で集める
