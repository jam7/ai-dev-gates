# 40: 追跡ドキュメントからの参照の書き方

追跡ドキュメント (docs/、TODO.md、memory など「現在の正」や「残作業」を書く場所)
から、コードや変更をどう指すかのルール。きっかけは実事故: 実データ除去の
filter-repo 一発で、文書内のコミットハッシュ 25 個が全滅し、**誰も気づかなかった**
(死んだハッシュはビルドもテストも全ゲートも通る。ただの文字列なので検査対象がない)。

### REF-1: コミットハッシュを追跡ドキュメントに書かない [MUST] [構造]
- 対象: docs/ 配下・TODO.md・memory 等の追跡ドキュメント。notes/ (追記のみの
  作業記録) は対象外 — あちらは「書いた時点の記録」であり、腐ることが許される
- 規則: コミットハッシュ (`9626a4b` 等) で変更を指さない。代わりに:
  - 実装の場所 → **ファイルとシンボル名** (`git log -S` で変更も引ける)
  - 進捗の記録 → **説明文そのもの** (ハッシュは情報を足していない)
  - 特定の変更 → **コミットの件名** (履歴書き換えに耐え、`git log --grep` で引ける)。
    spec-dev を使う PJ ではコミットメッセージの **D-ID** も同じ役割を果たす
- 理由: ハッシュは (1) 履歴書き換えで**一斉に**死ぬ (2) 読んでも意味が分からず
  レビューで素通りする (3) 黙って腐る — しかも生死は機械でも判定できない。
  amend で捨てたコミットはローカルに ~90 日残るので `git cat-file` は通るが、
  どのブランチからも到達できず **clone には存在しない**
- 悪い例: `直した (3da7ef7)` — この参照は書いた当日に amend で実質死んだ
  / 良い例: `直した ("check-private: never scan the allow file"、2026-08-11)`

### REF-2: 別リポジトリの変更を指さない [MUST] [構造]
- 対象: 追跡ドキュメントと memory
- 規則: 他リポジトリのコミットは、ハッシュでも件名でも参照しない。必要なら
  **内容を要約して自分の側に書く**
- 理由: 参照元と参照先の片方しか手元に無いことがあり、どちらからも検証できない。
  相手側の履歴書き換えはこちらから観測すらできない

機械チェック: `tools/check-refs.py` が追跡ドキュメント内のハッシュ様文字列
(hex 7-40 文字で英字と数字の両方を含む) を生死を問わず検出する。日付や十進 ID は
拾わない。チェックサム等のわざと置く hex は `tools/refs-allow.txt` に理由付きで
宣言する (cq-baseline.txt と同じ契約)。
