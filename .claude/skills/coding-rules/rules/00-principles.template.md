# 00: 基本原則 — Clean Code / Readable Code (デフォルト)

cq-review Skill の `references/checklist.md` (関数化・重複 / 結合度・凝集度 /
制御フロー / 命名 / エラー処理 / コメント / テスト容易性) を、
**「書く側のルール」として適用する**。チェックリストはレビュー観点の形で
書かれているが、「その観点で指摘されないコードを最初から書く」と読み替える。

## 特に守るもの [構造 = ルール優先]

- **関数は 20-30 行を目安**にする。理想は「関数名と変数名が説明になっていて、
  コードだけで読めてコメントが要らない」状態で、そこまで削れると実質 20 行になる。
  30 行を超えそうになったら、書き進める前に分割・ガード節・構造体化を検討する
- **60 行は上限であって合格ラインではない**。cq-metrics.py の既定閾値が 60 なのは、
  既存コードに後から入れても指摘が溢れないための下駄。「60 行以内だから問題なし」
  とは判断しない。レビューでは `--max-func-lines 30` で測り直すとよい
- ネストは 4 段以内、引数は 5 個以内 (こちらは cq-metrics.py の既定と同じ)。
  引数も 5 は上限であって理想ではない。**理想は 0-2 個**で、3 個を超えそうなら
  関連する引数の構造体化を検討する
- 8 行以上のコピペをしない。同じコードを 2 回書きそうになったら関数化を検討する。
  ただし「同じ理由で同時に変わるか」で判断し、偶然似ているだけのコードは共通化しない
- エラーの握りつぶし (無視される戻り値・空 catch) を書かない

## 分割のコツ [構造 = ルール優先]

長くなった関数をどこで切るかの指針。「切る場所」は行数ではなく責務で決める:

- **切り出した関数に「何をするか」の名前が付かないなら、切る場所が間違い**。
  名前が付く単位 = 責務の単位。`processData2` や `helperA` しか思いつかない
  切り出しは、切り直しの合図
- **呼び出し側が読み下せる文になるか**で切り方を確かめる。分割後の呼び出し列が
  手順書のように読める (`load → validate → apply`) のが正しい分割。読んで
  流れが分からなくなったら、その分割は抽象度が揃っていない
- **ヘルパー関数・ラムダ式・関数オブジェクトを活用する**。低レベルの繰り返し
  (走査・比較・変換) に名前を付けて本流から追い出すと、本流が抽象度の揃った
  流れになる。形は言語の慣用に従う (C++ ならラムダ/関数オブジェクト、Python
  なら内部関数や小さなトップレベル関数)
- **切り出した関数が相手側のデータばかり触るなら、置き場所はそちら側**
  (Feature Envy)。自分のクラスより他クラスの getter を多く呼ぶ関数は移動候補

## 細部の原則 [細部 = 既存コードの流儀優先]

- 名前から挙動が予想できるようにする。単位・条件は名前に含める (timeout_ms など)
- コードから分かることをコメントに書かない。分からないこと (なぜ・制約・単位) を書く
- コメントアウトでコードを残さない。消す (履歴は git が持っている)
