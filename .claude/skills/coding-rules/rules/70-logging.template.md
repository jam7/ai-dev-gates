# 70: ログとエラーの扱い

握り潰さないことは 00-principles にもあるが、**握り潰していないつもりで
握り潰す**書き方がいくつかあるので、そこを名指しする。

### LOG-1: 標準出力へ直接書かず、ログ機構を通す [MUST] [細部]
- 対象: 全言語。使い捨てスクリプトは除く
- 規則: 出力はプロジェクトのログ機構を通す。**出力先の決定は起動時の 1 か所**に
  集め、書く側は「何を」だけを決める
- 理由: 標準出力へ直接書く関数 (`print`、`console.log`、`fprintf(stderr, ...)`
  など) は宛先を選べないので、ファイルへ残したくなった日に全部を書き換える
  ことになる。レベルで絞ることもできない
- 悪い例: `print("load failed: " + err)` / 良い例: `log.warning("load failed",
  err, stack)`

### LOG-2: catch ではエラーと発生箇所の両方を渡す [MUST] [構造]
- 対象: 例外を持つ全言語。戻り値でエラーを返す言語も、エラー値と発生箇所を
  同じように扱う
- 規則: 捕まえた中身をログに出すとき、**メッセージだけで済ませない**。
  エラーオブジェクトとスタックトレースを一緒に渡す。スタックの取り方は言語で
  違う (別の引数として捕捉時に渡る言語もあれば、自身が持つ言語もある)
- 理由: メッセージだけだと、どこで起きたのか分からない。スタックを捨てた瞬間に
  「その行に到達した経路」が失われ、調査は当て推量に落ちる
- 悪い例: `catch (e) { log.warning("load failed"); }`
  / 良い例: `catch (e) { log.warning("load failed", e, stack); }`

### LOG-3: 誰に伝えるかは、その層が正を持つかで決める [MUST] [構造]
- 対象: 全言語。アプリとライブラリが同じリポジトリにある場合は特に
- 規則: **ライブラリは投げる** (throw / rethrow、エラーを返す) — 何を見せるかは
  呼び出し元の判断。**アプリは記録し、かつ画面に出す**。フォールバックのために
  捕まえるときは、何でも受ける形にせず**具体的な型**で受ける
- 理由: ライブラリが黙って既定値を返すと、呼び出し元は失敗を知る手段を失う。
  逆にアプリが記録だけして黙ると、利用者は成功したと受け取る。**手元に正がある
  操作は黙ってもよいが、正が向こうにある操作で黙るのは嘘になる**
- 悪い例: 型を書かない catch で `return fallback;` だけ返す
  / 良い例: `catch (ParseError e) { log.warning("...", e, stack); return
  fallback; }`

### LOG-4: うるさいログはレベル設定で抑える。出さない形にしない [SHOULD] [構造]
- 対象: 全言語
- 規則: ログが多すぎるときは、**どのログ源をどのレベルまで通すか**の設定を
  見直す。呼び出し側で握り潰す、warning に昇格させて素通りさせる、といった
  迂回をしない。抑えるときは「次に同じ調査をするとき何で代替するか」を
  決めてから抑える
- 理由: 迂回は 2 つを壊す。**必要なログまで一緒に消える**ことと、
  「なぜここだけ warning なのか」を後から誰も説明できなくなること
- 悪い例: 詳細ログを消すために呼び出し箇所を削る
  / 良い例: 起動時の設定でそのログ源だけ WARNING 以上にし、理由をコメントに書く
