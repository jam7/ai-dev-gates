# 30: テストの待ち方

テストが落ちたときに**一番高くつくのは、原因がテスト自身にある場合**。実装を
疑って調べ回った末に「マシンが忙しかっただけ」に行き着く。その形をあらかじめ
潰すためのルール。

### TEST-1: 時間ではなく条件を待つ [MUST] [構造]
- 対象: 全言語・全テスト
- 規則: 固定の待ち時間 (`sleep` / `Future.delayed` / `Thread.sleep` /
  `setTimeout`) で「このころには終わっているはず」を表現しない。**条件が
  満たされるまで短い間隔で確認し、上限を超えたら失敗**させる。上限は
  「本当に壊れていれば必ず超える」値でよく、正常時は待たない
- 理由: 固定の待ちは**マシンの負荷次第で足りなくなる**。しかも足りなかった
  ときの症状は「その機能が壊れている」に見えるので、無関係な変更を疑うことに
  なる。かといって余裕を持たせるとテスト全体が遅くなる。両方を同時に外す
  方法が条件待ちしかない。並列実行するテストでは、**自分の変更が別ファイルを
  落とす**形で現れるので特に見つけにくい
- 悪い例: `await Future.delayed(Duration(milliseconds: 80)); expect(fetched.length, 12);`
  / 良い例: `await waitUntil(() => fetched.length == 12);` (上限つき)

### TEST-2: 待ちたくなったら、まず境界を疑う [SHOULD] [構造]
- 対象: 全言語・全テスト
- 規則: 待ち時間を数え始めたら、その前に**テスト対象が本物の外界 (ファイル・
  ネットワーク・時計) を触っていないか**を確認する。触っているなら、待ち方を
  工夫する前に、その境界を差し替えられるようにする (インメモリ実装・fake) 方を
  検討する
- 理由: 待ちは症状で、原因は「単体テストのつもりの場所に本物の I/O がある」
  こと。差し替えれば待ちは 0 になり、速く確定的になる。TEST-1 は原因を
  消せないときの受け皿であって、最初に選ぶ手ではない
- 悪い例: 実ファイルに書くストアを UI のテストから呼び、完了を実時間で待つ
  / 良い例: メモリ上のファイルシステムを注入し、フレームを進めるだけで終わらせる

### TEST-3: 偽の時計と本物の I/O を混ぜない [MUST] [構造]
- 対象: 偽時計を持つテスト機構 (Flutter の `testWidgets`、`fakeAsync`、
  Jest の fake timers など)
- 規則: 偽時計の下で本物の I/O を `await` しない。**完了は永久に来ない**。
  実 I/O を確かめたいテストは偽時計のない普通のテストで書き、UI 側のテストでは
  境界を差し替える
- 理由: 症状はハングやタイムアウトで、原因から最も遠い所に出る。逃げ道
  (Flutter なら `runAsync`) はあるが、そこへ逃げた時点で実時間待ちに戻るので
  TEST-1 の問題を呼び込む。逃げ道を使うなら、なぜ境界を差し替えられないのかを
  コメントに書く
- 悪い例: `testWidgets` の中で実ファイルへの書き込みを `await` する
  / 良い例: 実 I/O は `test()` に置き、`testWidgets` にはインメモリ実装を渡す
